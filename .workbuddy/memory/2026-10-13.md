## 诊断：用户自行启动后端报 WinError 10013（实为端口冲突，不是权限）

现象：用户在 `H:\work\rag-backend` 下分别用 `uvicorn app.main:app --reload --port 8000` 和
`.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000` 启动，均报
`ERROR: [WinError 10013] 以一种访问权限不允许的方式做了一个访问套接字的尝试。`

根因：**本会话后台起的 rag-backend 实例（PID 25704）仍占着 `127.0.0.1:8000`**，属端口冲突。

证据：
- `netstat -ano -p tcp` → `127.0.0.1:8000  LISTENING  25704`（python.exe，工作集 1.8 GB），即上一节那个"会话结束后会停止"的实例，实际并未退出。
- venv python 直连绑定：`127.0.0.1:8000` → errno **10048**；`0.0.0.0:8000` → **成功**。
  即占用者绑的是**具体地址**，通配地址仍能绑——这正是出现 10013 而非 10048 的原因。
- `netsh int ipv4 show excludedportrange protocol=tcp` 仅 `50000-50059`，**8000 不在排除范围** → 排除 Hyper-V/WSL2 端口保留。

规律（Windows 特有，写进 MEMORY）：与占用者绑定**同一个具体地址**时，若双方都设了 `SO_REUSEADDR`，
bind 返回 **WSAEACCES(10013)**；未设时返回 **WSAEADDRINUSE(10048)**。
→ **在 Windows 上看到 10013，第一嫌疑是端口被占，不是防火墙/权限**。

处置：`taskkill //F //PID 25704` → 8000 立即释放 → 带 `SO_REUSEADDR` 重绑 `127.0.0.1:8000` 成功，端口交还用户自行启动。
另提示：`--reload` 在 Windows 上会派生子进程（reloader + worker），重载瞬间更易出现端口继承/占用假象，排查时先去掉它。

## 全站删除按钮加 loading 与防重复提交

用户要求「点击删除按钮增加 loading 状态，禁止重复提交」。三个页面三个入口，改造前状态不同：

| 页面 | 触发方式 | 改造前问题 |
| --- | --- | --- |
| Documents | 受控 `<Modal>` + `onOk={() => void handleDelete()}` | onOk 返回 undefined → antd **不加 loading**，确认按钮可连点，删除中还能取消/关闭 |
| KnowledgeBase | Dropdown 菜单 + `modal.confirm` | antd 自动 loading，但删除进行中**行内菜单仍可再点**，能开出第二个确认框 |
| Conversations | 卡片按钮 + `modal.confirm` | 同上，删除中卡片按钮可再点 |

### 改造方案（统一模式）
- **受控 state + ref 双轨**：`deletingId`（UI：按钮 loading/disabled、菜单项冻结）+ `deletingRef`（真正的重入开关）。
  **关键认知：`modal.confirm` 的 `onOk` 闭包在弹窗创建时就固定了，读不到最新的 state，防重复判断必须走 ref**；受控 Modal 的 onOk prop 每次渲染都更新，用 state 即可。
- Documents：`deleting` state + 守卫 + `confirmLoading` + `okButtonProps/cancelButtonProps.disabled` + `closable={!deleting}` + onCancel 拦截（删除中禁止关闭）。
- KnowledgeBase：删除中冻结整行 Dropdown（三项全部 disabled，删除项显示「删除中…」，行按钮 loading）。
- Conversations：卡片删除按钮 `loading={deletingId === item.id}`、其余卡片 disabled。
- `onOk` 始终返回 Promise → antd 给确认按钮自动加 loading（confirm 场景靠 antd 内部拦截点击，不写 disabled 属性——实测如此，见下）。

### 端到端验证（`.workbuddy/tmp/verify-delete-loading.mjs`，可复用）
核心技巧：**用 CDP `Fetch.enable` + `requestPaused` 把 DELETE 请求人为延迟 2.5s**，把"删除中"这个瞬间拉长成可采样的窗口。
- 场景 A（文档）：真实上传 → 删除。删除中确认按钮 `ant-btn-loading` + `disabled:true`、取消禁用、右上角 X 消失；**强制派发 3 次 click（绕过 disabled）后仍是 1 次 DELETE 请求**；行消失。截图 `11-delete-loading.png`。
